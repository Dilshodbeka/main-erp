# Финансы PRO — под-проект A: «Oylik va qarzlar» (фиксированный оклад, авансы, помесячный баланс)

**Дата:** 2026-11-05
**Статус:** утверждён владельцем по секциям (1–5), ожидает ревью этого документа
**Владелец решений:** собственник бизнеса (Aliya ERP)
**Реализация:** не начата до вашего «да» на этот документ

## Програма «Финансы PRO»

Запрос владельца по финансам разложен на пять под-проектов. Каждый получает свою спецификацию, свой план
реализации и свою миграцию живой базы. Порядок согласован: **A → C → D → B → E**, при этом E достраивается
блоком после каждого шага, чтобы пульт директора наполнялся сразу.

| Код | Под-проект | Состояние |
|---|---|---|
| **A** | Фиксированный оклад + авансы + помесячный баланс работника с кассой | этот документ |
| **C** | Расходы месяца (коммуналка, кухня/столовая, уличные/аутсорс-услуги) с муррадатом и долгом «как по поставщикам» | отдельная спецификация |
| **D** | Займы и инвестиции от знакомых/внешних лиц: отдельный внутренний счёт, перевод в основной, частичные возвраты | отдельная спецификация |
| **B** | Работник как клиент услуг и материалов, с погашением из зарплаты | отдельная спецификация |
| **E** | Пульт директора: где лежат деньги, что должно прийти, кому должны, будущие приходы и расходы | отдельная спецификация |

## Решения, зафиксированные владельцем

1. **Только фиксированный оклад.** Сдельные начисления (ставка × принятые этапы) остаются в системе как
   статистика выработки, но с месяца запуска плана больше не создают денег.
2. **Запуск с текущего месяца (2026-11).** Уже накопленные невыплаченные сдельные суммы не пропадают:
   они становятся переносным остатком с собственной проводкой и видимым «осталось сколько».
3. **FIFO.** Любой платёж закрывает самое старое обязательство: сначала переносный остаток, потом ноябрь,
   потом декабрь и далее. Излишек становится `Oldindan berilgan` («выплачено вперёд») и сам закрывает будущий
   месяц.
4. **Неоплаченный месяц копит долг.** Обязательство считается полным месяцем для активного работника и долей
   по дням для месяца увольнения; долг висит в «кому должны», пока не погашен. При снятии с работы остаток
   замораживается и отображается отдельно.

## Цель

У каждого работника есть свой оклад и свой баланс с кассой. Админ видит помесячную сетку «оплачен / частично /
не оплачен», сколько дал авансов и в каком месяце, и сколько компания должна работнику сейчас. Работник видит
только свою сетку. Директор — одну цифру общего долга по зарплате, которая сходится с кассой.

## Архитектура

Расчёт — чистая функция, состояние — минимальное. Месячные обязательства **не хранятся**, а выводятся из плана
оклада, дат активности и уже существующих кассовых записей. Платежи остаются обычными `CashEntry`
(`direction: 'out'`, `source: 'payroll'`, `sourceId: employeeId`), поэтому вся история выплат до перехода
остаётся валидной и попадает в FIFO без переноса данных.

Новый модуль `src/salary.ts` не импортирует UI и не хранит состояние — по тому же принципу, что
`src/receivables.ts` (там уже реализован FIFO по отгрузкам клиентов).

## Модель данных

export interface Employee {
  id: string;

  // существующие поля не меняются; добавляется ровно одна коллекция:

Версия `State` остаётся `4`. Новая коллекция поднимается по образцу `recipes`
(`src/migrations.ts:124`): `Array.isArray(source.salaryPlans) ? source.salaryPlans : []`, а `deactivatedAt` —
`employee.deactivatedAt ?? null`. Живые снимки, облачные копии и `erp_snapshot` от этого не ломаются: старый
снимок получает пустой список окладов и `null`-даты.

`deactivatedAt` сделан необязательным (`?`) намеренно: в репозитории 21 литерал `Employee` в 13 файлах
(тесты домена, синхронизации, миграций, документов, истории, отчётов, выписок, диагностики, доступа, гайда и
`CatalogSettings.tsx`), и обязательное поле заставило бы править их все без пользы для дела. Движок читает
`employee.deactivatedAt ?? null`, поэтому отсутствие поля и `null` означают одно и то же — работник работает.
`salaryPlans` при этом обязателен: ни одного литерала `State` в коде нет, все состояния приходят из `emptyState()`.

## Расчёт: `src/salary.ts`

```ts
export interface SalaryMonth { month: string; obliged: number; paid: number; unpaid: number }
export interface SalaryLedger {
  employeeId: string;
  carryOver: number;   // Hisoblangan, lekin to‘lanmagan eski qoldiq (plan oylikdan oldingi davr)
  carryOverPaid: number; // shu qoldiqdan FIFO bo‘yicha yopilgan summa
  months: SalaryMonth[];
  prepaid: number;     // oldindan berilgan: ochiq majburiyatlardan ortiqcha to‘lov
  owed: number;        // kompaniya xodimga hozir qarz
  paidTotal: number;   // xodimga barcha to‘lovlar (CashEntry out, source payroll)
  plannedTotal: number;
}
export function salaryLedger(state: State, employeeId: string, asOf?: string): SalaryLedger
```

Правила, по порядку. Пункт 1 — ветка «плана нет», она самодостаточна; пункты 2–6 описывают ветку «план есть».

1. **Нет плана → цифры не меняются.** Если у работника нет ни одной `SalaryPlan`, `months = []`,
   `carryOver = round(Σ принятых `PayrollEntry` работника − Σ его зарплатных платежей)` (та же формула, что
   сейчас в `src/domain.ts:404-407`, пересчитанная напрямую по `state.payroll` и `state.cash`), и
   `owed = carryOver`. `src/salary.ts` **не импортирует `src/domain.ts`** (иначе будет цикл: domain вызывает
   ledger) — ему нужен только тип `State`. Это держит все существующие проверки в `src/domain.test.ts` и все
   компании, где оклады ещё не включены. **Отсечки по нулю в этой ветке нет:** `owed` может быть отрицательным
   (переплата), как и сегодня, — иначе менялись бы метрика `payrollTotal` и уже покрытые тесты.
   Тогда же `payrollDebt(state, employeeId)` в `src/domain.ts` становится тонким фасадом
   `salaryLedger(state, employeeId).owed` — с планом он отдаёт `owed` (начисления после `startMonth` в него не
   входят), без плана — ровно прежнюю формулу. Все шесть мест UI (`src/App.tsx:401,419,519,536,583,638`) и
   `src/components/WidgetBoard.tsx:35` меняются не потому, что их правят, а потому, что меняется функция под
   ними.
2. **Граница перехода.** `startMonth` = минимальный `fromMonth` среди версий плана работника.
   `accruedBefore` = сумма принятых `PayrollEntry` с `createdAt < startMonth-01`.
   `paidBefore` = сумма выплат `source: 'payroll'` с `createdAt < startMonth-01`.
   `carryOver = max(0, round(accruedBefore - paidBefore))` — обязательство, поставленное на
   `startMonth-01`. Отрицательного `carryOver` не бывает: переплата до перехода автоматически уходит в
   закрытие первых месяцев плана тем же FIFO.
3. **Обязательство по месяцам.** Для каждого календарного месяца от `startMonth` до месяца `asOf`
   (по умолчанию — текущий месяц) включительно: `amount` = версия плана, действующая в этом месяце;
   `obliged = round(amount × activeDays / daysInMonth)`; `obliged = 0`, если месяц начинается после
   `deactivatedAt`.
   `activeDays` режется только по `deactivatedAt`. Дата приёма на работу не хранится, поэтому **первый месяц
   плана начисляется целиком** — доля по дням есть только для месяца увольнения.
4. **FIFO.** Обязательства упорядочены `[carryOver, M1, M2, …]`; платежи (`source: 'payroll'`, включая
   сторно как отрицательные) отсортированы по `createdAt` и заполняют их по порядку. Остаток после последнего
   открытого месяца = `prepaid`. `unpaid = max(0, obliged - paid)` по каждому месяцу.
5. **Итоги.** `plannedTotal = accruedBefore + Σ obliged` (всё, что начислено работнику за всю историю),
   `paidTotal` — все зарплатные платежи нетто (сторно вычитаются, в том числе до `startMonth`). Отсюда идентичность
   для ветки «план есть» (пункты 2–5): `owed = max(0, plannedTotal − paidTotal)`,
   `prepaid = max(0, paidTotal − plannedTotal)`. В ветке «плана нет» (пункт 1) отсечки по нулю нет:
   `owed` = знакочистый нетто и может быть отрицательным, `prepaid = 0` — иначе поменялись бы метрика `payrollTotal`
   и уже покрытые тесты. `carryOverPaid = min(pool, carryOver)` — часть платежей, ушедшая на
   переносный остаток, где `pool = max(0, paidBefore − accruedBefore) + (paidTotal − paidBefore)`. При сторно платежа,
   выданного до `startMonth`, `pool` уходит в минус и `carryOverPaid` вместе с ним; это осознанно: clamp в движке ломает
   идентичность готовности. Витрина показывает `max(0, carryOverPaid)`, SQL-зеркало — дословно `min(pool, carryOver)`
   без `GREATEST`. Из FIFO следует, что
   `Σ месячных unpaid + (carryOver − carryOverPaid) = owed` — это проверяется тестом.
   (`plannedTotal` не может быть `carryOver + Σ obliged`: платёж до `startMonth` уже уменьшил `carryOver`, и вторая
   форма вычла бы его дважды — долг каждого работника оказался бы меньше настоящих.)
6. **Округление.** Все деньги через существующий `round()` (2 знака). Сумма месяцев может отличаться от
   `amount × количество месяцев` на копейки — это принято; `Σ платежей` с кассой сходится точно.

Горизонт: будущие месяцы обязательств не создают. `prepaid` просто лежит и начинает расходоваться, когда
месяц наступает.

## Команды

```ts
| { type: 'salary.plan.set'; employeeId: string; amount: number; fromMonth: string }
| {
  type: 'salary.pay';
  employeeId: string; amount: number; account: Account;
  kind: 'advance' | 'payroll'; note: string; allowPrepay: boolean;
}
```

Обе — только для admin (гейт `src/domain.ts:1253` не меняется; работник по-прежнему может вызывать только
`work.accept`, `work.start`, `work.submit`).

`salary.plan.set`
- `employeeId` существует; `amount` — число ≥ 0 с 2 знаками; `fromMonth` формата `YYYY-MM`.
- Версия с тем же `fromMonth` уже есть → **заменяет** её `amount` (правка оклада или опечатки).
- Версии с другим `fromMonth` добавляются как новый ярус; порядок действия считается по `fromMonth`, а не по
  порядку добавления.
- Правка суммы месяца, по которому уже были платежи, разрешена и перекладывает сетку задним числом — это
  осознанный компромисс выбранного подхода; журнал амалов (`AuditEntry`) показывает, кто и когда менял.
- Удаления версии в этом под-проекте нет (ошибочный план правится суммой или новой версией).

`salary.pay`
- пишет `CashEntry { direction: 'out', source: 'payroll', sourceId: employeeId, note }`, а `category`
  берётся из `kind` (см. ниже); это единственный способ выдачи зарплаты из интерфейса;
- `amount > 0`, `account` в `(cash, bank)`, `note` ≤ 200 символов;
- остаток кассы проверяется как обычно: `postCash` (`src/domain.ts:545`) отклоняет любой `out`, если сумма больше баланса счёта
  (`Insufficient account balance`). Аванс не обходит этот потолок — выдать вперёд можно только те деньги, которые лежат на счёте;
- без `allowPrepay` отклоняется `Payment exceeds payable`, если `amount > owed`; с `allowPrepay` излишек
  уходит в `prepaid`. Флаг нужен ровно для «зарплата вперёд» (`oldindan to‘lov`);
- `kind` решает `category` кассовой записи: `'payroll'` для полной выплаты, `'advance'` для аванса. На деньги
  не влияет — `source` остаётся `'payroll'`, и отчёт операционных расходов фильтрует по
  `source !== 'manual'` (`src/reports.ts:80`), поэтому новый `category` не может удвоить расход;
- журнал кассы печатает `category` как есть (`src/App.tsx:534`), поэтому добавляю `cashCategoryLabel` в
  `src/i18n.ts`: `Ish haqi`, `Avans`, `Mijoz to‘lovi`, `Yetkazib beruvchi`, `Qo‘lda kiritilgan`, а для введённых
  админом категорий — текст как есть. Функция должна покрывать оба исторических написания: TS пишет `payroll` / `sale`,
  а `erp_execute` (`supabase/schema.sql:2040`) всегда писал `Payroll payment` / `Supplier payment` — старые проводки из
  облака приходят вторым вариантом. Это заодно убирает нынешнюю сырую латиницу `payroll` / `sale` в узбекском
  интерфейсе;
- уволенному работнику платить можно (долг существует именно для этого).

`payroll.pay` остаётся принятой в домене и в SQL (история), но UI туда больше не ходит. `payment()`
(`src/domain.ts:551-567`) для зарплатного пути берёт payable из `salaryLedger(...).owed`; инвариант сторно
(`src/domain.ts:1151`) переписывается на `check(salaryLedger(state, sourceId).owed >= 0, ...)`.

Новая панель в «Xodimlar» (`src/sections.ts:16`): `{ id: 'oylik', title: 'Oylik va qarzlar' }`.

  чекбокс `Oldindan to‘lovga ruxsat` с подписью, что излишек закроет следующий месяц.
- Роль работника: видит те же чипы только по себе (маршрут `panel === 'ish-haqi'` для не-admin уже ведёт в

- Текст интерфейса — узбекская латиница, валюта UZS. Фиксированный словарь: `Oylik`, `Hisoblangan`,

  `To‘liq to‘lov`, `Oldindan to‘lovga ruxsat`, `Ishdan chiqqan`, `to‘langan`, `qisman`, `to‘lanmagan`.

## Сервер и хранение

Чтобы живая база не расходилась с демо, синхронно меняются:

- `supabase/schema.sql` — таблица `erp_salary_plans(id uuid, company_id, employee_id, amount numeric(14,2),
  from_month text, created_at timestamptz)` c RLS-политикой как у остальных `erp_*` и индексом
  `(company_id, employee_id, from_month)`; колонка `deactivated_at date null` в `erp_employees`;
  секция `salary_plans` в `erp_snapshot()`; case-ы `salary.plan.set` и `salary.pay` в `erp_execute`.
- Функция `erp_salary_ledger(company_id, employee_id)` на plpgsql, повторяющая правила 1–6, — сервер обязан
  отклонить платёж больше `owed` так же, как TS-домен. Паритет сверяется PGlite-зондом на одинаковых данных.
- `_shared/backup.ts` — `STATE_COLLECTIONS` += `salaryPlans` (иначе копия и восстановление потеряют оклады).
  Таблица `erp_salary_plans` попадает в дамп автоматически, потому что список таблиц берётся из
  `erp_backup_tables()`; проверяется зондом, а не на слово.
- `src/migrations.ts` — дефолт `[]` для новой коллекции и `deactivatedAt ?? null`; `src/sync.ts:25` — `salaryPlans`
  в список коллекций, которые `verifiedSnapshot` требует от серверного снимка. Отсюда порядок выката: сначала миграция
  живой базы (иначе каждый облачный снимок будет отклонён), потом публикация фронтенда;
- `supabase/schema.sql:518-524` — `erp_salary_plans` в массив DO-блока, который включает RLS и `erp_admin_read`
  (иначе таблица останется без политики);
- демо-сид (`src/seed.ts`) — 2–3 плана и один снятый с работы работник с остатком;
- `src/sync.ts` не меняется: очередь команд универсальна.

## Обработка ошибок

- Невалидный `fromMonth` (не `YYYY-MM`, не безопасная дата) → `Invalid salary plan month`.
- `amount` с третьим знаком или отрицательный → `Invalid amount` (тот же `round`-инвариант, что и в остальном
  домене).
- Платёж больше `owed` без флага → `Payment exceeds payable` (существующий текст, UI его показывает).
- План для несуществующего работника → `Employee not found`.
- `deactivatedAt` задан, но работник снова активен → команда `employee.update` снимает дату; несогласованность
  невозможна на уровне состояния.
- Сторно выплаты (`cash.reverse`) автоматически увеличивает `owed` и откатывает FIFO-распределение месяца.

3. переносный `340 000` + план → `carryOver = 340 000`, `owed = 1 540 000`; платёж `800 000` →
   `carryOverPaid = 340 000`, ноябрь закрыт на `460 000`, `owed = 740 000`;
4. `deactivatedAt = 2026-11-15` (30 дней) → ноябрь `600 000`;
5. первый месяц плана = полный месяц, даже если чип стоит на 20-е число (даты приёма нет);
6. платёж `2 000 000` при `owed = 1 800 000` и `allowPrepay` → `prepaid = 200 000`, `owed = 0`;
7. тот же платёж без флага → `Payment exceeds payable`;
8. две версии (`1 200 000` с `2026-11`, `1 500 000` с `2027-01`) → ноябрь и декабрь по `1 200 000`,
   январь по `1 500 000`;
9. сторно выплаты возвращает сумму в `owed`;
10. выплата до `startMonth` уменьшает `carryOver`, а не месяцы плана.

## Критерии готовности

- Полоса месяцев по каждому работнику сходится с кассой: `owed = max(0, plannedTotal − paidTotal)`,
  `prepaid = max(0, paidTotal − plannedTotal)` и `Σ месячных unpaid + непогашенный переносный остаток = owed`.
- Метрика «MAJBURIYATLAR» и «Kreditor qarzdorlik» показывают сумму, равную Σ `owed` по всем работникам.
- Работник видит только свою сетку; ни в одном экране чужие суммы не появляются.
- Компания, где ни у кого нет плана, даёт ровно те же числа, что и до изменения (проверяется тестом 1).
- Облачная копия содержит `salaryPlans` и восстанавливается без потерь.

## Вне рамок этого под-проекта

Налоги, пенсионные начисления, больничные, отпускные, табель, печать расчётного листка, валюты кроме UZS,
автоматическое закрытие месяца по расписанию, доля по дням при приёме на работу (нужна — добавим `startedAt`
отдельным шагом), роль продавца (#114), склады и перемещения (#116), бригадные этапы (#115).

## Риски

1. **Расхождение TS и SQL.** Паритет держится PGlite-зондом; без него живой клиент и сервер считают разное.
2. **Перекладка сетки задним числом** после правки суммы или сторно. Решение принято сознательно; смягчается
   подсказкой в UI и журналом амалов.
3. **Миграция живой базы.** Перед применением — облачная копия (панель «Резервные копии» уже работает),
   прогон зондом, отдельное разрешение владельца. Публикация `dist` — тоже только по отдельному разрешению.
