# Telegram-чат в Aliya ERP

Двусторонний чат с клиентом из карточки клиента: текст, файлы (PDF, изображения, DWG/DXF, архивы), индикатор непрочитанных, звук и всплывающее уведомление о входящем. Бот предназначен только клиентам. Работник ничего не привязывает и ничего не получает в Telegram — свои заказы и расчёты он видит в своём аккаунте в приложении.

По состоянию на 3 ноября 2026 года: `supabase/telegram.sql` применён к боевому проекту (перед этим снят полный снимок `erp_*`), функции `telegram-webhook` (без проверки JWT) и `telegram-send` задеплоены, фронтенд опубликован. Осталось шагами 3 и 4 ниже: три секрета (`TELEGRAM_BOT_TOKEN`, `TELEGRAM_BOT_USERNAME`, `TELEGRAM_WEBHOOK_SECRET`) и вызов `setWebhook` — их выполняет владелец, потому что токен не должен попадать ни в файлы проекта, ни в журнал агента. Пока секреты и webhook не заданы, чат в CRM работает на запись, но бот молчит: ответы приходят с ошибкой `telegram_not_configured`.

## Что где лежит

| Файл | Назначение |
| --- | --- |
| `supabase/telegram.sql` | Таблица сообщений, поля Telegram в `erp_customers`, индексы, RLS, приватный bucket `telegram-files`, публикация Realtime. В конце скрипта — блок удаления очередей и полей работника, оставшихся от прежней сборки. |
| `supabase/functions/_shared/telegram.ts` | Чистые функции: разбор update, санитизация имён, лимиты, проверка путей, формы данных. Импортируется и в браузер, и в Edge Functions. |
| `supabase/functions/telegram-webhook/index.ts` | Приём update от Telegram: привязка клиента по `/start <code>`, входящие сообщения, скачивание файлов, дедупликация повторов. |
| `supabase/functions/telegram-send/index.ts` | API из CRM: отправка текста и файла, отметка прочитанным, ссылка для привязки, ручная привязка и отвязка, подписанные ссылки на файлы. |
| `src/chat.ts` | Клиентский слой: демо-хранилище, облачный транспорт, ошибки, подписка на изменения. |
| `src/components/TelegramChat.tsx` | Панель чата и компонент счётчика непрочитанных (`ChatBadge`). |
| `src/App.tsx` | Точки входа: кнопка в карточке клиента, в заказе, бейджи в канбане и таблице, звук и тост. |

## Порядок подключения

### 1. Бот в BotFather

1. `/newbot`, получить токен. Токен хранится только в секретах Supabase — не в браузере и не в `.env` фронтенда.
2. Запомнить username бота без `@` — он нужен для ссылки `https://t.me/<username>?start=<code>`.
3. Webhook ставится из шага 4, вручную через интерфейс BotFather его ставить не нужно.

### 2. SQL

Применять после `supabase/schema.sql`, в SQL Editor авторизованного проекта, при наличии резервной копии. Скрипт идемпотентен: повторный запуск пересоздаёт ограничения, индексы и политики.

Что создаётся:

- `erp_customers.telegram_chat_id`, `telegram_link_code`, `telegram_link_expires_at` с проверками формата.
- Глобально уникальные индексы `telegram_chat_id` и `telegram_link_code` — один Telegram-чат не может принадлежать двум компаниям.
- `erp_messages` с проверками длины текста (4096), размера файла (20 МБ), типа отправителя и содержимого.
- Уникальный частичный индекс по `telegram_update_id` — повторный webhook-вызов не создаёт дубль.
- RLS: читать сообщения может только администратор своей компании; `anon` и другие роли доступа не имеют.
- Приватный bucket `telegram-files` с лимитом 20 МБ; загрузка и чтение только для администратора и только внутри префикса своей компании.
- Публикация Realtime для `erp_messages` (только если на хосте есть `supabase_realtime`).

Отдельный блок в конце скрипта удаляет всё, что относилось к уведомлениям работнику: триггеры `erp_notify_task` / `erp_notify_order` / `erp_notify_line`, функции `erp_notify*`, таблицу `erp_notifications` и три telegram-поля в `erp_employees`. На чистой базе эти `DROP … IF EXISTS` ничего не делают, на базе, где прежняя версия уже была применена, — подчищают её. Таблица очереди удаляется вместе с её строками: история уведомлений работника не сохраняется, она и не была частью учёта.

### 3. Секреты Edge Functions

```bash
supabase secrets set \
  TELEGRAM_BOT_TOKEN=<токен из BotFather> \
  TELEGRAM_BOT_USERNAME=<username без @> \
  TELEGRAM_WEBHOOK_SECRET=<случайная строка 32+ символа>
```

`SUPABASE_URL` и `SUPABASE_SERVICE_ROLE_KEY` платформа подставляет сама. Не добавляйте их в `VITE_*`.

### 4. Деплой функций и webhook

```bash
# Webhook вызывается Telegram, а не пользователем: JWT платформы отключается.
supabase functions deploy telegram-webhook --no-verify-jwt

# Отправка вызывается из CRM с JWT пользователя: JWT включён.
supabase functions deploy telegram-send

curl -X POST "https://api.telegram.org/bot<TOKEN>/setWebhook" \
  -H "content-type: application/json" \
  -d '{
    "url": "https://<project-ref>.supabase.co/functions/v1/telegram-webhook",
    "secret_token": "<TELEGRAM_WEBHOOK_SECRET>",
    "allowed_updates": ["message"]
  }'
```

Проверка: `curl "https://api.telegram.org/bot<TOKEN>/getWebhookInfo"` должен вернуть тот же `url` и пустой `last_error_message`.

### 5. Фронтенд

Достаточно уже описанных `VITE_SUPABASE_URL` и `VITE_SUPABASE_ANON_KEY`. Без них приложение работает в деморежиме, и чат тоже демонстрационный.

## Как привязывается клиент

1. Оператор открывает карточку клиента → кнопка Telegram → «Havola yaratish». Сервер создаёт одноразовый код на 24 часа.
2. Клиент открывает ссылку и нажимает Start. Webhook проверяет код, срок, занятость чата и записывает `telegram_chat_id`.
3. Альтернатива без ссылки: оператор вводит числовой chat ID вручную. Username и телефон не принимаются.
4. «Uzish» очищает привязку; история сообщений остаётся.

## Почему у работника нет Telegram

Решение владельца: бот — канал общения с клиентами. Работник входит в систему под своим email и паролем (карточка доступа), и там ему видны назначенные этапы, количество, сроки и начисленная оплата. Производство не меняет ход оттого, что кто-то прочитал сообщение: этап принимается в цехе или в приложении, а не в чате.

Что из этого следует для кода:

- В карточке доступа нет кнопки Telegram, одноразовой ссылки работника и кнопки «Xabarlarni yuborish» — остаются «Parol», «O‘chirish» и «Yangilash».
- `telegram-webhook` не ищет код привязки среди работников и не отвечает на сообщения работника: незнакомый чат получает подсказку привязаться через карточку клиента.
- Ни один триггер не пишет очередь событий, поэтому доставлять работнику сообщения нечего и `flush` не нужен.
- Текст `/start` без кода: «Assalomu alaykum! Bu bot korxona mijozlari bilan aloqa uchun…».

## Поток сообщений

Входящее: Telegram → `telegram-webhook` (проверка `x-telegram-bot-api-secret-token`, дедупликация по `update_id`) → строка в `erp_messages` → Realtime → открытая панель и бейджи. Файл скачивается в фоне, кладётся в `telegram-files`, в строку пишутся путь и подписанная ссылка на 7 дней. Webhook всегда отвечает `200`, чтобы Telegram не зациклил повторы.

Исходящее: браузер → загрузка файла в bucket (если файл) → `telegram-send` с JWT → проверка профиля администратора и компании → Bot API → запись строки с `sender = 'operator'`.

Непрочитанное: входящие пишутся с `is_read = false`. Открытие панели отмечает их прочитанными только если они действительно есть, иначе получился бы цикл обновлений. Счётчики агрегируются в `chatOverview` и показываются в навигации, канбане, таблице заказов и на кнопке чата.

## Безопасность

- Токен бота и `service_role` не покидают сервер. В браузер попадают только публичные `VITE_*`.
- `telegram-send` требует валидный JWT и роль `admin` в `erp_profiles`; иначе 401/403. Все действия ограничены компанией администратора.
- `telegram-webhook` не проверяет JWT, но требует секретный заголовок, сравнение постоянного времени.
- Чтение сообщений — только администратор своей компании (RLS). Сотрудник и экран цеха чат не видят.
- `telegram_chat_id` есть только у клиентов: один аккаунт бота не может одновременно быть работником, сводить две роли в webhook не нужно.
- Файлы: белый список расширений, лимит 20 МБ, санитизация имён, запрет `..`, `\`, `//`; путь обязан начинаться с префикса компании.
- Ответы бота не раскрывают, существует ли чат другой компании.
- Ошибки функций пишут только имя класса ошибки, без токена и URL скачивания.

## Деморежим

Хранилище — `localStorage['aliya-erp-telegram-v1']`, событие `aliya-chat-change`. Для первых двух клиентов создаются тестовые переписки. Лимит файла — 1 МБ, файл хранится как data URL. Кнопки «Kiruvchi (demo)» и «Mijoz «Start» bosdi (demo)» позволяют проверить входящее сообщение, звук, тост и привязку без Telegram.

## Коды ошибок в интерфейсе

| Код | Текст для оператора |
| --- | --- |
| `telegram_not_configured` | Telegram bot hali sozlanmagan. |
| `telegram_chat_not_found` / `telegram_blocked` / `telegram_forbidden` | Клиент заблокировал бота либо закрыл доступ. |
| `telegram_chat_taken` | Этот chat уже привязан к другому клиенту. |
| `no_chat_link` / `already_linked` / `link_expired` | Привязка отсутствует, уже сделана или истекла. |
| `empty_message` / `message_too_long` | Пустой текст или больше 4096 символов. |
| `file_type_not_allowed` / `file_too_large` / `demo_file_too_large` | Тип или размер файла не подходит. |
| `table_missing` | Не применён `supabase/telegram.sql`. |
| `access_denied` | Нет роли администратора. |
| `network` | Нет связи с сервером. |

## Ограничения и что не проверено

- Живой обмен с Telegram не проверялся: функции задеплоены, но секреты и `setWebhook` на момент написания этого раздела ещё не заданы, поэтому ни один update от Bot API не проходил через `telegram-webhook`. Bot API и Deno в среде разработки недоступны.
- Подписанные ссылки на файлы в облаке не тестировались на живом хранилище.
- Если в прежней сборке вы уже применяли `telegram.sql` с очередью работнику, повторный запуск удалит `erp_notifications` и telegram-поля `erp_employees` безвозвратно. Фронтенд и функции этих объектов больше не читают. На боевом проекте их никогда не создавали, поэтому блок удаления прошёл вхолостую и ничего не удалил — это проверено запросом перед применением.
- Проверено локально: `tsc`, `vitest` (включая тесты `chat` и `telegram`), PGlite-прогон `telegram.sql` (в том числе проверка, что после скрипта у работника не осталось telegram-полей, очередей, индексов, функций и триггеров, и что пол и отмена позиции работают как раньше), `vite build`, ручной сценарий в браузере (отправка, вложение, превью, привязка по ссылке, отвязка, бейджи, тост, мобильный вид).
- Модуль не даёт гарантий доставки: если клиент заблокировал бота, сообщение останется только в CRM.
