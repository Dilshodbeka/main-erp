# Права доступа, продавцы, склады и цеха — дизайн

**Дата:** 2026-11-16
**Статус:** согласовано владельцем по секциям (1–4), ожидает вычитки спецификации
**Пакеты:** A (права и продавцы) → B (склады и дефицит) → C (снабжение) → D (цеха)

## 1. Задача

Владелец ведёт мебельное производство и продаёт систему другим. Сейчас в системе три роли
(`admin`, `worker`, `display`) и один склад. Нужно:

1. Настраивать доступы сотрудников пресетами и галочками: продавцы, кассиры, кладовщики,
   мастера, доставщики — по несколько человек каждого.
2. Несколько складов с независимыми остатками и перемещениями.
3. Несколько цехов/участков внутри одной компании.
4. Рабочий сценарий дефицита: в заказе несколько материалов, часть есть, часть нет;
   докупается во время производства; остатки меняются до завершения заказа.

Главное ограничение владельца: при настройке должно быть легко добавлять склады, продавцов
и цеха, «и на систему особо не было изменений». Поэтому все расширения — измерения
и права, а не новые параллельные подсистемы. Пока сущность одна (один склад, один цех) —
интерфейс выглядит как сегодня.

## 2. Решения владельца

| Вопрос | Решение |
|---|---|
| Модель прав | Пресеты + галочки |
| Несколько складов | Отдельный остаток + перемещения |
| Несколько производств | Цеха/участки внутри компании |
| Продавец: видимость | Видит всех клиентов и заказы, меняет только своих |
| Клиенты без ответственного | Продавец берёт клиента кнопкой «Mening mijozim» |
| Порядок работ | A → B → C → D, каждый пакет выкатывается отдельно |

## 3. Общие принципы

- Три системные роли сохраняются: `admin` — владелец, `worker` — сотрудник с личным
  профилем, `display` — ТВ-экран. Продавец, кассир, кладовщик, начальник цеха — это
  `worker` с набором прав и привязкой к сотруднику/цеху/складу.
- Права проверяются на сервере (`erp_execute`, `erp_snapshot`), а не только в интерфейсе.
  Интерфейс скрывает недоступное, сервер отказывает.
- Все новые поля аддитивные, с безопасным значением по умолчанию. Старый интерфейс,
  офлайн-очередь и ранее сохранённые snapshot продолжают работать между применением SQL
  и деплоем.
- Один склад/один цех — ноль новых элементов в интерфейсе.
- Язык интерфейса — узбекская латиница, суммы UZS. Отчёты владельцу — на русском.

## 4. Пакет A — права доступа и продавцы

### 4.1. Данные

`erp_profiles` получает:

```sql
permissions jsonb NOT NULL DEFAULT '[]'::jsonb
  CHECK (jsonb_typeof(permissions) = 'array'),
scope_workshop_ids jsonb NOT NULL DEFAULT '[]'::jsonb
  CHECK (jsonb_typeof(scope_workshop_ids) = 'array'),
scope_warehouse_ids jsonb NOT NULL DEFAULT '[]'::jsonb
  CHECK (jsonb_typeof(scope_warehouse_ids) = 'array')
```

Пустой scope = «все» в рамках выданного права. Ограничение действует только вместе
с правом; само по себе пустое поле ничего не запрещает.

`Customer` получает `sellerId: string | null` (сотрудник-продавец, ответственный за клиента).
Колонка `erp_customers.seller_id uuid` с FK на сотрудника компании; `NULL` — легаси-клиент
без ответственного.

Клиентский `Actor` получает необязательные поля:

```ts
interface Actor {
  id: string; name: string; role: Role; companyId: string;
  permissions?: string[];      // пусто/undefined = права по роли (legacy worker)
  workshopIds?: string[];      // пусто = все
  warehouseIds?: string[];     // пусто = все
}
```

Сервер всегда возвращает оба массива (для админа — полный набор ключей).
`src/sync.ts` принимает отсутствие полей как пустые массивы.

как работник.

Владелец (`admin`) имеет полный доступ и не редактируется через панель.

### 4.4. Правила продавца

- `orders.view_all` = видит всех клиентов, все заказы, историю, но **не** себестоимость
  и не зарплаты.
- Редактирование заказа/услуги разрешено, если `orders.edit_all`, либо `orders.edit_own`
  и `customer.sellerId === actor.id`. `order.cancel`, `orderLine.cancel`, `order.update`,
  `order.launch` проверяют это же условие.
- Создание заказа: продавец может создать заказ любому клиенту; если у клиента нет
  ответственного, клиент автоматически закрепляется за ним при создании заказа
  (при наличии `customers.claim`).
- «Mening mijozim»: команда `customer.claim { customerId }`; succeeds только если
  `sellerId IS NULL` и у актора есть `customers.claim`. Иначе — ошибка
  «Bu mijoz allaqachon biriktirilgan».
- Владелец/`customers.assign` может переназначить или снять ответственного:
  `customer.assign { customerId, sellerId: string | null }`.
- Карточка клиента и список показывают ответственного, если он есть. Для клиента без
  ответственного продавцу с правом показывается кнопка «Mening mijozim».
- Фильтр «Mening mijozlarim» в CRM — только у не-админа с `orders.edit_own`.

### 4.5. Сервер

- Новый SQL-хелпер `erp_has_permission(p_profile, p_key) returns boolean`:
  `role='admin'` → true; иначе `permissions ? p_key`.
- `erp_execute`: убрать жёсткий whitelist для `worker`; вместо него карта
  «тип команды → требуемое право» (см. 4.6). `display` остаётся read-only.
  `work.accept/start/submit`, `ticket.create/reply` разрешены любому `worker`
  всегда (в пределах своих этапов), независимо от `permissions`. Остальные команды
  требуют права; пустой массив = прежнее поведение работника.
- `erp_snapshot`: `v_admin` остаётся полным доступом. Для остальных:
  - `suppliers`, `purchases`, `reports`, `payroll`, `salaryPlans`, `expensePlans`,
    `loans`, `workerDeductions` — только при соответствующем праве;
  - `cash`: при `cash.view` — все записи; иначе только `source='sale'` с
    `customer_id` из видимых клиентов. Это нужно, чтобы карточка клиента и долг по
    заказу считались правильно; баланс кассы без `cash.view` интерфейс не показывает;
  - `stockMovements`: видны всем, кроме `display` (нужны для расчёта остатков и
    дефицита), но `unitCost` обнуляется без `cost.view`, `note` скрывается;
    для ТВ-экрана движения не отдаются, как сейчас;
  - `items.cost`, `lastPurchasePrice`, `materialCost`, `laborCost`,
    `orders.price/overhead/markup`, `materials.estimatedCost/actualCost`,
    `tasks.rate/supplierCost/salePrice` — только при `cost.view` (для админа — всегда);
    `items.minQty` остаётся видимым: от него зависят предупреждения о пополнении;
  - `payroll`/`salaryPlans` — только при `salaries.view`;
  - `workerDeductions` — только строки видимых клиентов: они участвуют в расчёте
    долга клиента-сотрудника, поэтому нужны продавцу с `payments.customer`,
    но не раскрывают оклады и начисления;
  - клиенты и заказы: при `orders.view_all` — все, иначе только заказы клиентов,
    где `seller_id = employee_id`, плюс заказы со своими этапами (текущее поведение);
  - `customers.phone/address` остаются видимыми продавцу с `orders.view_all`;
  - в отчётах без `cost.view` блоки прибыли и себестоимости не отдаются (нули и
    пометка «ruxsat yo‘q» в UI).
- `erp-access` (Edge Function): принимает `permissions`, `scopeWorkshopIds`,
  `scopeWarehouseIds`; валидирует ключи по белому списку; владелец-only; пишет аудит
  `access.create` / `access.update`. Смена пароля и удаление — как сейчас.
- `erp_current_profile()` возвращает новые поля автоматически (`%ROWTYPE`).

### 4.8. Миграция A

`20261118_access_permissions.sql`:

1. `alter table erp_profiles add column if not exists permissions jsonb not null default '[]'::jsonb` + check.
2. Аналогично `scope_workshop_ids`, `scope_warehouse_ids`.
3. `alter table erp_customers add column if not exists seller_id uuid` + FK `(company_id, seller_id)`.
4. Индекс `erp_customers(company_id, seller_id)`.
5. `create or replace function erp_has_permission(...)`.
6. Обновлённые `erp_snapshot`, `erp_execute` (полные тела, идемпотентно).
7. Backfill: существующие `worker` остаются с пустым массивом → прежние права.
   `admin` не меняется.

### 4.9. Критерии приёмки A

- Владелец создаёт продавца пресетом, тот видит всех клиентов, но не может
  редактировать чужой заказ; свой — может.
- Продавец без `cost.view` не видит себестоимость и прибыль ни в одном ответе API.
- Легаси-клиент без ответственного закрепляется кнопкой «Mening mijozim»; после
  этого другой продавец его не редактирует.
- Кассир видит кассу и принимает оплату, но не видит закупки и зарплаты.
- Работник без прав ведёт себя точно как до пакета A (те же 5 команд, тот же экран).
- Существующие 36 файлов тестов проходят без изменения ожиданий.

## 5. Пакет B — склады и дефицит

### 5.1. Данные

```ts
interface Warehouse { id: string; name: string; active: boolean }
```

`State.warehouses: Warehouse[]`. Основной склад имеет детерминированный id
`00000000-0000-4000-8000-00000000a001` — один и тот же в SQL-миграции и в клиентской
константе `src/warehouse-default.ts`. При пустом списке клиент подставляет запись
«Asosiy ombor» с этим id, поэтому старый локальный snapshot и офлайн-очередь
не ломаются.

Новые поля:

- `StockMovement.warehouseId: string`; в `source` добавляется `'transfer'`
- `Purchase.warehouseId: string` (куда приходовать)
- `Order.warehouseId: string` (откуда выдавать материалы)
- `MaterialLine` не меняется: склад определяется заказом.
- `Purchase.orderId?: string | null` — появляется в пакете C, колонка создаётся там.

`stockQty(state, itemId, warehouseId?)` и `reservedQty(state, itemId, warehouseId?)`:
без аргумента склада — сумма по всем складам (текущая семантика), с аргументом —
только этот склад. Все новые вызовы в производстве и дефиците передают склад заказа.

### 5.2. Поведение

**Запуск заказа.** `order.launch` больше не блокируется отсутствием материалов.
Сохраняются проверки: заказ черновик, материалы уникальны, не выданы, материал не
принадлежит другому клиенту, операция/исполнитель существуют и активны.
Дефицит не мешает запуску.

**Выдача материалов.** `order.issue` выдаёт столько, сколько есть на складе заказа:

- по каждой невыданной строке `take = min(qty - issuedQty, max(0, stock − резервы других заказов))`;
- `take = 0` — строка пропускается, остаётся в дефиците;
- если хотя бы одна строка получила `take > 0` — команда успешна, создаются движения;
- если по всем строкам `take = 0` — ошибка «Omborda material yo‘q. Qoldiqni to‘ldiring»,
  но заказ остаётся в производстве;
- `issuedQty += take`, `actualCost` — по фактически выданному;
- резерв «своего» заказа не мешает выдаче: считается `stock − резервы других заказов`.

Проверка `Insufficient reserved stock` удаляется. Дефицит после выдачи отражается
в `orderShortage` и в интерфейсе.

**Смена склада заказа.** `order.update` может изменить `warehouseId`, только пока
ни по одной строке нет выдачи (`issuedQty === 0` у всех материалов). После первой
выдачи поле заблокировано: иначе уже списанное окажется не на том складе.

**Резервы.** Резерв — невыданный остаток производственных заказов на складе заказа.
Отмена заказа возвращает только фактически выданное, как сейчас.

**Дефицит.** `orderShortage(state, order)` считает по складу заказа и дополнительно
возвращает `suggestedFrom: { warehouseId, available }[]` — где этот материал есть
свободно. Интерфейс дефицита показывает «Bor: Asosiy ombor — 2 litr» и кнопку
«Ko‘chirish».

**Перемещение.** Новая команда:

```ts
{ type: 'warehouse.transfer'; itemId: string; fromId: string; toId: string; qty: number; note: string }
```

Проверки: оба склада активны и разные, `qty > 0`, свободный остаток
`stock − резервы` на складе-источнике достаточен. Пишутся два движения с
`source: 'transfer'`: `out` из источника и `in` в приёмник, `unitCost` — текущая
средняя себестоимость позиции. Себестоимость позиции (`Item.cost`) не меняется —
она общая по компании; склады различают количество, не цену.

**Инвентаризация.** `inventory.count` получает `warehouseId?` (по умолчанию основной):
сверяет и корректирует остаток выбранного склада, не может опуститься ниже резерва
этого склада.

**Закупка.** `purchase.create` получает `warehouseId?`; `purchase.receive` приходует
в склад закупки. Средневзвешенная себестоимость остаётся общей по компании.
Закупка в другой склад видна в остатках этого склада; перенос — перемещением.

**UI.** Со вторым складом:

- в «Ombor» появляется селектор склада (по умолчанию «Asosiy ombor»), остатки и
  анализ — по выбранному;
- в редакторе заказа — «Qaysi ombordan» (только для черновика; после первой выдачи
  поле заблокировано с подсказкой);
- в закупке — «Qaysi omborga»;
- в дефиците — кнопка «Ko‘chirish» с предзаполненным перемещением;
- в настройках — панель «Omborlar»: добавить, переименовать, отключить. Нельзя
  удалить склад с движениями и нельзя отключить последний активный.

Пока склад один — селекторов нет, все операции идут на основной.

### 5.3. Миграция B

`20261119_warehouses.sql`:

1. `create table erp_warehouses (id, company_id, name, active)` + уникальность имени в компании.
2. Для каждой компании — строка «Asosiy ombor», если нет ни одной.
3. `alter table erp_stock_movements add column warehouse_id uuid`; backfill основным
   складом компании; `set not null`; FK.
4. То же для `erp_purchases`, `erp_orders`.
5. Индексы `(company_id, warehouse_id)`.
6. Обновлённые `erp_snapshot` (массив `warehouses`, поле `warehouseId`) и `erp_execute`
   (частичная выдача, перемещение, склад в закупке/инвентаризации).
7. `erp_cash` и деньги не затрагиваются.

### 5.4. Критерии приёмки B

- Заказ с тремя материалами, из которых есть два, запускается; выдача списывает два
  и оставляет третий в дефиците.
- После прихода третьего материала повторная выдача списывает только его.
- Заказ не может уйти в минус и не может съесть резерв другого заказа.
- Перемещение уменьшает остаток источника и увеличивает приёмника, сумма по компании
  не меняется, себестоимость не меняется.
- Инвентаризация одного склада не трогает второй.
- При одном складе интерфейс не отличается от текущего.
- Тесты `material-issue.test.ts` обновлены под частичную выдачу без изменения
  доменных инвариантов (резерв, себестоимость, возврат при отмене).

## 6. Пакет C — снабжение

### 6.1. Сводная потребность

Модуль `src/supply.ts`:

```ts
interface SupplyNeed {
  itemId: string; name: string; unit: string;
  warehouseId: string; short: number;
  orders: { id: string; number: string; dueDate: string; short: number }[];
  lastPurchasePrice: number;
}
```

Собирает `orderShortage` по всем заказам в статусе `production`, группирует по
`(itemId, warehouseId)`, сортирует по величине дефицита и ближайшему сроку.

Новая панель «Ta’minot ehtiyoji» в разделе «Ombor» (или «Xaridlar» — на этапе плана
выбирается по месту в навигации). Строка: материал, склад, «yetishmaydi N», заказы,
кнопка «Xarid qilish».

### 6.2. Закупка из дефицита

- Кнопка открывает существующую форму закупки с предзаполненными строками:
  материал, `qty = short`, `price = lastPurchasePrice`.
- Поставщик обязателен, как сейчас; если у позиции есть последний поставщик — он
  подставляется.
- Закупка получает необязательный `orderId` — только для трассировки «под какой заказ
  покупали». На склад, резервы, деньги и себестоимость не влияет.
- После приёма закупки строка дефицита уменьшается; в заказе снова доступна выдача.

### 6.3. Данные и миграция C

- `Purchase.orderId?: string | null`; колонка `erp_purchases.order_id uuid` nullable,
  FK на заказ компании.
- `purchase.create` принимает `orderId?`; проверка — заказ той же компании.
- Если к моменту реализации C пакет B ещё не выкачен — миграция C дополняет B,
  но порядок фиксирован: B раньше C.

Миграция `20261120_supply.sql`.

### 6.4. Критерии приёмки C

- Сводная потребность показывает все активные заказы, а не только выбранный.
- Закупка из строки создаётся с правильным количеством и складом.
- Приём закупки уменьшает дефицит и разблокирует выдачу.
- Деньги не меняются до оплаты поставщику.
- Закупка без `orderId` работает как раньше.

## 7. Пакет D — цеха

### 7.1. Данные

```ts
interface Workshop { id: string; name: string; active: boolean }
```

`State.workshops: Workshop[]`; основной цех имеет детерминированный id
`00000000-0000-4000-8000-00000000b001` — одинаковый в SQL-миграции и в клиентской
константе `src/workshop-default.ts`. При пустом списке клиент подставляет
«Asosiy ishlab chiqarish» с этим id.

Новые поля:

- `Machine.workshopId: string`
- `Operation.workshopId: string`
- `RouteLine.workshopId: string`

Цех станка и операции выбирается в справочнике. У операции цех берётся от станка;
если станок не задан (ручная операция), цех указывается явно. При создании/ревизии
заказа `RouteLine.workshopId` копируется с операции и дальше не меняется сам —
перенос операции в другой цех не переписывает историю заказов. Шаблоны маршрутов
не хранят цех: он проставляется из операции при применении шаблона.

### 7.2. Экран «Sex»

- Один цех — как сейчас, без табов.
- 2+ цеха — табы «Barchasi» и по одному на цех; выбор запоминается в localStorage.
- Заказ виден в колонке цеха, к которому относится его текущий незавершённый этап.
  Заказ с этапами в двух цехах виден в обоих, но показывает только этапы своего цеха.
- Счётчики шапки — по выбранному цеху.
- Карточка заказа в «Barchasi» показывает цех у каждого этапа.

### 7.3. ТВ-экран

- `erp_profiles.scope_workshop_ids` для `display` — необязательный фильтр показа.
- Пусто — все заказы, как сейчас. Задан — только заказы, у которых есть этап
  в этих цехах.
- Привязка настраивается при создании/редактировании ТВ-аккаунта.
- Фильтр показа не даёт прав и не меняет read-only.

### 7.4. Начальник цеха

- Пресет «Sex boshlig‘i» (пакет A) + обязательный scope цехов.
- Видит все этапы своих цехов, принимает/бракует результат (`work.review`),
  видит брак своих цехов, выдаёт материалы по заказам своих цехов.
- Не видит себестоимость, зарплаты и чужие цеха.
- Один начальник может вести несколько цехов (массив scope).
- Личный терминал работника не меняется: исполнитель по-прежнему сотрудник.

### 7.5. Миграция D

`20261121_workshops.sql`:

1. `create table erp_workshops`.
2. Для каждой компании — «Asosiy ishlab chiqarish».
3. `workshop_id` в `erp_machines`, `erp_operations`, `erp_tasks`; backfill основным
   цехом; `not null`; FK.
4. `erp_snapshot`: массив `workshops`, поле `workshopId`, фильтрация ТВ по scope.
5. `erp_execute`: проверка scope для `work.review` и выдачи материалов начальником.

### 7.6. Критерии приёмки D

- При одном цехе экран «Sex» и ТВ не меняются.
- После создания второго цеха появляются табы; заказ с этапами двух цехов виден
  в обоих, но с разными этапами.
- Начальник цеха принимает только этапы своего цеха; чужой этап сервер отклоняет.
- ТВ с привязкой показывает только свой цех.
- Перенос операции в другой цех не меняет уже запущенные заказы.

## 8. Порядок выката

| Пакет | SQL | Что выкатывается | Зависит от |
|---|---|---|---|
| A | `20261118_access_permissions.sql` | права, пресеты, продавцы | — |
| B | `20261119_warehouses.sql` | склады, частичная выдача, перемещения | A (права) |
| C | `20261120_supply.sql` | сводная потребность, закупка из дефицита | B |
| D | `20261121_workshops.sql` | цеха, табы, ТВ-scope, начальник цеха | A |

Правила:

1. Владелец применяет SQL в Supabase SQL Editor, затем деплой `npm run deploy`.
2. Между SQL и деплоем старый интерфейс продолжает работать: все новые поля аддитивные.
3. Перед каждым пакетом: `npx tsc -b`, `npx vitest run`, `npm run build`, прогон
   сценария пакета в демо-режиме.
4. Живой SQL и деплой — только по отдельному разрешению на каждый пакет.
5. Пакеты можно ставить с паузой, чтобы владелец проверил на реальной работе.

## 9. Совместимость и миграция клиента

- `src/sync.ts`: в обязательные массивы snapshot добавляются `warehouses` (B)
  и `workshops` (D); отсутствие массива трактуется как пустой и заполняется
  дефолтной записью. `State.version` остаётся 4: изменения аддитивные.
- Локально сохранённый snapshot и офлайн-очередь читаются через `normalizeState()`:
  недостающие `warehouseId`/`workshopId` заполняются id основного склада/цеха.
- Команды с необязательным складом/цехом при отсутствии поля используют основной.
- Контрактный тест `snapshot` проверяет наличие новых полей и массивов.

## 10. Тестирование

Для каждого пакета:

- **Домен (vitest):** правила продавца, права в `applyCommand` (если actor без права —
  ошибка), частичная выдача, резервы по складам, перемещение, инвентаризация,
  сводная потребность, цех этапа.
- **PGlite-зонд:** миграция применяется на копии живой схемы, старые строки получают
  основной склад/цех, новые команды пишут ожидаемые строки.
- **Контракт snapshot:** новый массив и поля присутствуют, маскировка по правам
  не отдаёт себестоимость и зарплаты.
- **UI (демо-режим):** сценарий пакета в браузере, при одном складе/цехе — отсутствие
  новых элементов.
- **Регрессии:** полный `vitest run` и `npm run build`.

## 11. Риски и меры

| Риск | Мера |
|---|---|
| Заказ запущен без материалов и «завис» | Виджет «Nazoratda» и дефицит показывают такие заказы; выдача доступна в любой момент |
| Частичная выдача ломает расчёт себестоимости | `actualCost` только по `issuedQty`, тесты на отпуск и отмену |
| Резервы между складами считаются дважды | Все проверки получения/выдачи — в разрезе склада заказа, сумма по компании — только для отчётов |
| Продавец видит лишнее через API | Маскировка в `erp_snapshot`, а не только скрытие в UI; контрактный тест |
| Легаси-клиенты без продавца | Кнопка «Mening mijozim», владелец может назначить вручную |
| Перемещение съедает резерв | Проверка свободного остатка на складе-источнике |
| Новый цех «переписывает» старые заказы | Цех копируется в этап при запуске и не пересчитывается |
| Несколько SQL-пакетов применяются не по порядку | Фиксированный порядок A→B→C→D, проверка `schema_migrations` перед каждым |

## 12. Вне рамок

- Несколько касс/счетов как отдельные сущности — касса и банк остаются общими;
  несколько кассиров работают с ними через права.
- Склад внутри цеха — материалы берутся с обычного склада.
- Перемещение заказа между складами после первой выдачи — только возврат и повторная
  выдача либо перемещение материала.
- Раздельная нумерация заказов по цехам — номера общие.
- Мультивалютность, несколько компаний на одного пользователя.
- Изменение правил оплаты поставщикам и аутсорса.

## 13. Открытые вопросы

Нет. Все развилки по правам, складам, дефициту и цехам закрыты владельцем
(секции 1–4). Детали размещения панелей (например, «Ta’minot ehtiyoji» в «Ombor»
или «Xaridlar») решаются на этапе плана без изменения бизнес-правил.
