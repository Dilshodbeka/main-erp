# Развёртывание Aliya ERP

Документ фиксирует контракт сборки и порядок публикации. Конфигурация подготовлена локально; ни база Supabase, ни хостинг в рамках этой работы не изменялись и не публиковались.

## Требования

- Node.js 24 и npm.
- Отдельный проект Supabase для ERP.
- Хостинг Vercel или Netlify с поддержкой статической сборки Vite.

## Переменные окружения

В фронтенд попадают только два публичных значения:

```text
VITE_SUPABASE_URL=https://<project-ref>.supabase.co
VITE_SUPABASE_ANON_KEY=<publishable/anon key>
```

Правила:

- `service_role` и любые secret-ключи запрещены в браузере, репозитории и переменных `VITE_*`.
- Локально значения хранятся в `.env.local`; файл не коммитится.
- `.env.example` содержит только пустые имена переменных.
- Без переменных приложение работает в локальном деморежиме, данные хранятся только в браузере.

```bash

npm run preview
```

## Подготовка Supabase

Порядок обязателен:

1. Локально проверить SQL (`supabase/schema.sql`) на тестовой базе PGlite.
2. С согласия владельца данных сделать резервную копию удалённого проекта.
3. Применить схему в SQL Editor авторизованного проекта. Скрипт не выполняется автоматически при деплое.
4. В Authentication → Users создать пользователей email/пароль.
5. Войти этим пользователем в само приложение и ввести название компании на экране онбординга — вызывается `erp_bootstrap_company`, создаётся компания и профиль владельца. Из SQL Editor шаг не выполняется: функции нужна сессия Auth (`auth.uid()`).
6. Привязать сотрудников через `erp_link_worker`, экран цеха — через `erp_link_display`.
7. Проверить RLS: сотрудник видит только свои задания и начисления, экран цеха — только канбан без цен и денег.

### Управление доступами сотрудников

Владелец создаёт, сбрасывает пароль и удаляет входы сотрудников и ТВ прямо в приложении: «Sozlamalar → Kirish huquqlari». Логин остаётся email + пароль.

1. Развернуть функцию (проверка JWT включена по умолчанию):

   ```bash
   supabase functions deploy erp-access
   ```

2. Секрет `SUPABASE_SERVICE_ROLE_KEY` уже доступен функциям Supabase; в браузер и `VITE_*` он не попадает.
3. Функция сама проверяет профиль: только `admin` своей компании; роли `worker` и `display`; аккаунт владельца нельзя удалить или сбросить через панель.
4. Если функция не развёрнута, панель покажет понятное сообщение, остальная система продолжит работать.

### Модуль Telegram-чата

Порядок и полное описание — в [telegram-chat.md](telegram-chat.md). Кратко:

1. BotFather → новый бот, сохранить токен и username.
2. Применить `supabase/telegram.sql` после `schema.sql` (идемпотентно, с резервной копией).
3. `supabase secrets set TELEGRAM_BOT_TOKEN=… TELEGRAM_BOT_USERNAME=… TELEGRAM_WEBHOOK_SECRET=…`.
4. `supabase functions deploy telegram-webhook --no-verify-jwt` и `supabase functions deploy telegram-send`.
5. `setWebhook` с `secret_token` и `allowed_updates: ["message"]`; проверить `getWebhookInfo`.
6. Секреты бота не попадают в `VITE_*`, в браузер и в репозиторий.

Бот работает только с клиентами: карточка доступа работника ничего не привязывает и кнопок Telegram не содержит. Если прежняя версия модуля уже была применена, повторный запуск `supabase/telegram.sql` удалит очередь `erp_notifications`, функции `erp_notify*`, триггеры и telegram-поля в `erp_employees`. На боевом проекте этих объектов никогда не было, поэтому удаление прошло вхолостую.

## Резервные копии — собственный механизм ERP

Копию всей корпорации делает сама система и хранит её в приватном Cloudflare KV. Платный бэкап Supabase для этого не требуется.
Цепочка: приложение → Edge Function `erp-backup` (только сессия владельца) → внутренний HTTPS-шлюз Worker `erp-backup-gate` → неймспейс KV `ERP_BACKUP`.
Браузер не получает ни `SUPABASE_SERVICE_ROLE_KEY`, ни секрет шлюза и напрямую к хранилищу не обращается.
Бесплатных лимитов KV (1 ГБ, 100 000 чтений и 1 000 записей в сутки, значение до 25 МиБ) хватает с запасом: копия корпорации — сотни килобайт, запись — одна в сутки. Карта на аккаунте Cloudflare для KV не нужна (в отличие от R2, который требует подписки).

Что готово и что осталось (удалённые действия — только с отдельного разрешения владельца):

- `supabase/functions/_shared/backup.ts` — формат копии `company-copy`, сверка манифеста, sandbox-прогон `playbackCopy`, ретеншен `selectCopiesToDelete`, признак свежести.
- `supabase/migrations/20261104_backup_dump_restore.sql` — `erp_backup_dump` и `erp_backup_restore`: порядок таблиц берётся из `pg_constraint`, копируются только строки с `company_id` корпорации, `erp_companies` не затрагивается, execute разрешён только `service_role`. **Применено 4 ноября** через CLI; проверка — ниже, шаг 6.
- `supabase/functions/erp-backup/index.ts` — действия `put`, `list`, `get`, `verify`, `restore`. **Задеплоено**, версия 1, `ACTIVE`.
- `worker/backup-gate/index.ts` и `wrangler.backup.jsonc` — шлюз KV: PUT/GET/DELETE и `/__list` только по ключу `companies/<uuid>/…json`, всё под заголовком `x-erp-upload-secret`. Это отдельный Worker, поэтому `npm run deploy` сайта не может задеть хранилище. **Задеплоено**: `https://erp-backup-gate.doybek5557.workers.dev`, неймспейс `d59437a0e2ec46fc94bb38d292a01369`.
- Секрет шлюза `UPLOAD_SECRET` и `ERP_BACKUP_GATE_URL` / `ERP_BACKUP_GATE_SECRET` в Supabase — **заданы** (значение генерировалось через pipe и не сохранялось в файлы).
- `src/cloudBackup.ts`, `src/copyPanel.ts`, `src/components/BackupPanel.tsx` — транспорт, тексты баннера и панель «Sozlamalar → Baza va zaxira». **Ещё не опубликованы**: на Cloudflare лежит сборка от 3 ноября без панели, нужен `npm run deploy`.

Как это работает в приложении:

- При входе владельца `ensureDailyCopy` проверяет свежесть: если последней копии больше 36 часов — создаёт новую. При отказе (например, офлайн) проба повторяется на следующем изменении состояния, а не ждёт перезапуска.
- Хранение: все копии за 30 дней, затем по одной копии за каждый месяц ещё 12 месяцев, но не менее трёх копий всегда.
- «Tekshirish» читает файл и сверяет манифест со строками, ищет чужой `company_id`, сравнивает ревизию с `erp_metadata`, прогоняет блок состояния в песочнице и помечает копию, которая новее живой базы.
- «Qaytarish» требует вручную набранного слова `TIKLASH` и совпадения ожидаемой ревизии с живой; сначала живое состояние само кладётся в хранилище (копия безопасности), затем в одной транзакции удаляются строки корпорации (от зависимых таблиц к родительским) и вставляются из файла (от родительских к зависимым). Конфликт ревизии — ошибка, база не меняется.
- Раздел «Zaxira nusxalar (brauzer)» сохранён: JSON-файл и до 7 локальных снимков — переносимый дополнительный экземпляр, а не замена облачной копии.

## Откат

- Хостинг: вернуть предыдущий успешный деплой.
- База: «Qaytarish» из облачной копии нужного дня; копия, снятая вручную перед применением схемы, остаётся запасным путём.
- Секреты: при подозрении на утечку отозвать ключ в Supabase, заменить `UPLOAD_SECRET` шлюза и `ERP_BACKUP_GATE_SECRET` функции.

## Ограничения

- Автоматический деплой и применение SQL не выполняются этим репозиторием.
- Гарантии прибыли, юридической или налоговой корректности отсутствуют.
- Перед продажей другим компаниям нужны отдельный проект Supabase, собственные Auth-пользователи, проверка RLS и резервное копирование.
