# Маршрутизация: шаблоны маршрутов «услуга» vs «под ключ»

**Дата:** 2026-11-10
**Статус:** архитектура одобрена владельцем в диалоге; документ ожидает ревью владельца
**Реализация:** не начата; живые SQL-изменения и deploy не входят в этот документ

## 1. Цель и границы

Администратор создаёт именные **шаблоны маршрутов** — упорядоченные цепочки операций — двух типов: **«Xizmat»** (услуга, например покраска: Приём → Шлифовка → Покраска → Сушка → Выдача) и **«Mahsulot»** (под ключ: распил → заготовки → шлифовка/покраска → сборка). Шаблон применяется к позиции заказа одним действием и **копирует** свои этапы в позицию; заказ дальше хранит обычный маршрут и никакой ссылки на шаблон.

Первая версия включает:

- новую коллекцию `routeTemplates` в `State` и справочник шаблонов в «Sozlamalar»;
- создание/изменение/включение-выключение шаблонов только администратором;
- фильтр шаблонов по типу позиции (`Xizmat`/`Mahsulot`);
- автозаполнение ставки, цены клиенту и исполнителя при применении;
- применение с заменой маршрута позиции (с подтверждением при непустом маршруте);
- паритет офлайн-домена и серверного `erp_execute`, снимок и облачная копия включают шаблоны.

Первая версия **не** включает:

- авто-связку корпус + фасады в заказе под ключ (отдельная итерация);
- повсеместное инлайн-редактирование цен/ставок/параметров (отдельная итерация);
- материалы или нормы в шаблоне — нормы покраски уже применяются из справочника операций (Часть 2);
- отдельный документ/команду «применить шаблон» в домене — применение происходит в редакторе и сохраняется существующими `order.create`/`order.update`.

## 2. Согласованные правила

1. Шаблон — справочная сущность каталога уровня операций/рецептов; управляет только администратор.
2. Тип шаблона равен типу позиции (`product` | `service`). В редакторе позиции показываются только шаблоны подходящего типа.
3. Этап шаблона — ссылка на операцию (обязательна) плюс необязательные переопределения ставки и исполнителя.
4. При применении ставка этапа = `stage.rate ?? operation.workerRate`; цена клиенту = `operation.salePrice`.
5. Исполнитель при применении = явно заданный в шаблоне; иначе — единственный активный разрешённый работник операции; иначе остаётся пустым, и позицию нельзя сохранить, пока админ не выберет исполнителя (существующая проверка `positionIssue`).
6. Применение **заменяет** текущий маршрут позиции; если маршрут уже непуст, требуется подтверждение.
7. Заказ не хранит ссылку на шаблон — только скопированные этапы. Изменение или выключение шаблона не влияет на существующие заказы.
8. Количество этапа при применении равно количеству позиции (`stageQty = line.qty`), как в существующем `routeValues`.

## 3. Модель данных

### 3.1 Типы (`src/types.ts`)

```ts
export interface RouteTemplateStage {
  operationId: string;
  rate?: number;                    // переопределение ставки; иначе operation.workerRate
  executorKind?: ExecutorKind;      // 'employee' | 'supplier', необязательно
  employeeId?: string | null;
  supplierId?: string | null;
}

export interface RouteTemplate {
  id: string;
  name: string;
  kind: OrderLineKind;              // 'product' | 'service'
  active: boolean;
  stages: RouteTemplateStage[];     // упорядоченная цепочка, длина >= 1
}
```

`State` получает коллекцию `routeTemplates: RouteTemplate[]`.

Инварианты этапа: если `executorKind = 'employee'` и исполнитель задан — `employeeId` заполнен, `supplierId = null`; если `'supplier'` — наоборот. Этапы без `executorKind` интерпретируются как `'employee'` без исполнителя.

### 3.2 Команды

```ts
| { type: 'routeTemplate.create'; name: string; kind: OrderLineKind; stages: RouteTemplateStage[] }
| { type: 'routeTemplate.update'; templateId: string; name: string; kind: OrderLineKind; stages: RouteTemplateStage[]; active: boolean }
```

Жёсткого удаления нет — как у `Operation`/`Machine`/`Recipe`, шаблон выключается флагом `active`. Применение разрешено только к активному шаблону.

### 3.3 Применение (`src/order-editor.ts`, слой редактора)

Хелпер не меняет `State` и не создаёт доменную команду:

```ts
export function applyTemplate(state: State, template: RouteTemplate, qty: number): PositionStage[]
```

Для каждого этапа шаблона возвращает `PositionStage`:

- `operationId` — как в шаблоне;
- `rate` — `stage.rate ?? operation.workerRate`;
- `salePrice` — `operation.salePrice`;
- `executorKind` — `stage.executorKind ?? 'employee'`;
- `employeeId`/`supplierId` — явные из шаблона; если исполнитель-работник не задан, подставляется единственный активный разрешённый работник операции (`operation.employeeIds` ∩ активные работники, ровно один); иначе `null`;
- `qty` — `qty` позиции, `locked: false`, `completed: 0`.

## 4. Доменные расчёты

### 4.1 Валидация шаблона

`routeTemplateValues(state, input, exclude?)` (по образцу `operationValues`):

- имя обязательно и уникально среди шаблонов (без учёта регистра и пробелов, как `erp_operations_name_idx`);
- `kind` ∈ {`product`, `service`};
- `stages` непуст; каждая операция существует и активна;
- переопределение `rate` (если задано) — неотрицательная денежная сумма;
- исполнитель (если задан): `employee` — активный работник, авторизованный на операцию; `supplier` — существующий подрядчик; не допускаются два исполнителя или ноль при явном `executorKind`.

### 4.2 Паритет применения

Применение — чисто редакторская операция над копией; сохранение идёт существующими `order.create`/`order.update` → `routeValues`/`routeRevision`, поэтому все существующие проверки этапов (исполнитель, ставка, количество) применяются автоматически и повторно.

## 5. Интерфейс

Все новые подписи — узбекской латиницей, суммы — UZS.

### 5.1 Справочник «Sozlamalar → Marshrut shablonlari»

Список шаблонов: название, бейдж `Xizmat`/`Mahsulot`, число этапов, переключатель `Faol`. Кнопка **«Yangi shablon»** открывает модалку.

Редактор шаблона: название, тип (`Xizmat`/`Mahsulot`), упорядоченный список этапов — выбор операции, необязательные переопределение ставки и исполнитель (работник/подрядчик), кнопки добавить/удалить/сдвинуть этап. Сохранение — `routeTemplate.create`/`routeTemplate.update`.

### 5.2 Редактор заказа (позиция)

В `PositionForm` появляется кнопка **«Shablon»**, которая показывает только шаблоны, подходящие по типу текущей позиции, и активные. Применение заменяет `position.route` результатом `applyTemplate`; если маршрут уже непуст — подтверждение. После применения этапы обычные и редактируются как сейчас.

## 6. Supabase и офлайн-синхронизация

Одна новая идемпотентная миграция `supabase/migrations/20261110_route_templates.sql` обновляет `supabase/schema.sql` и применяется к живой базе только владельцем через SQL Editor после отдельного подтверждения.

- таблица `erp_route_templates(company_id, id, name, kind, active, stages jsonb)` с tenant-safe PK и CHECK `kind IN ('product','service')`;
- уникальный индекс `erp_route_templates_name_idx` на `(company_id, lower(btrim(name)))`;
- `erp_snapshot()` добавляет `routeTemplates` в возвращаемый JSON;
- `erp_execute` обрабатывает `routeTemplate.create` и `routeTemplate.update` с той же валидацией; работник управлять шаблонами не может;
- облачная копия (`erp_backup_dump_temp`) включает новую таблицу автоматически, как все `erp_*`.

Офлайн: `migrateState` принимает отсутствующую коллекцию как `[]` (по образцу `salaryPlans`/`loans`), версия `State` не меняется.

## 7. Ошибки и ограничения

Домен и SQL одинаково отклоняют при CRUD шаблона:

- пустое или неуникальное имя, некорректный `kind`;
- пустой список этапов, неизвестную или неактивную операцию;
- отрицательную ставку, неоднозначного исполнителя (два исполнителя или ноль при явном `executorKind`);
- неактивного/неавторизованного работника или неизвестного подрядчика;
- вызов `routeTemplate.*` работником.

Применение — операция редактора: неактивные шаблоны и шаблоны несовместимого типа просто не показываются в кнопке «Shablon».

Существующие ограничения на этапы (исполнитель обязателен, ставка и количество корректны) продолжают действовать при сохранении позиции.

## 8. Проверка

Реализация выполняется через RED → GREEN.

### Домен

- CRUD шаблона: создание, изменение, выключение; уникальность имени; ≥1 этап; неизвестная/неактивная операция; отрицательная ставка; неоднозначный исполнитель; неавторизованный работник; подрядчик;
- `applyTemplate`: fallback ставки на `workerRate`, цены на `salePrice`, автоподстановка единственного активного разрешённого работника, пустой исполнитель при 0 или нескольких, явный исполнитель из шаблона, замена маршрута;
- фильтр шаблонов по типу позиции;
- миграция состояния без коллекции `routeTemplates` не ломается.

### SQL / PGlite

- миграция применяется два раза без ошибок;
- снимок возвращает `routeTemplates` и round-trip совпадает с доменом;
- `erp_execute` отклоняет то же, что и домен; worker role не может управлять шаблонами;
- tenant isolation: чужой `company_id` не видит шаблоны;
- полный существующий PGlite-набор остаётся зелёным.

### UI и регрессии

- тесты редактора: показываются только шаблоны подходящего типа и активные; применение заполняет этапы; подтверждение при непустом маршруте;
- тесты справочника: создание/изменение/выключение шаблона;
- полный `npm test` и `npm run build` проходят;
- браузерная проверка в демо с пустыми `VITE_SUPABASE_*`: создание шаблона «услуга покраски», применение к позиции-услуге, сохранение заказа, запуск; desktop/mobile;
- production-публикация и живая миграция — только по отдельным разрешениям владельца, с отдельной проверкой после каждого шага.
